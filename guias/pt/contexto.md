# Contexto que continua no projeto


Quando uma conversa termina, o projeto precisa continuar compreensível. Guardar decisões nos arquivos ajuda a próxima pessoa ou agente a trabalhar com o que realmente existe.

| Documento | O que registrar |
| --- | --- |
| README | O que é o projeto, como abrir e o que está pronto. |
| Produto | Problema, público, fluxo principal e critério de entrega. |
| Instruções do projeto | Comandos válidos, convenções e limites do trabalho. |
| Arquitetura | Responsabilidades, dados, integrações e decisões importantes. |
| Design | Padrões visuais, estados e necessidades de acessibilidade. |
| Qualidade | Verificações, resultados, falhas conhecidas e limites. |
| Preparação | Dependências, versões e instruções de configuração. |

Use documentos existentes quando já cumprem esse papel. Criar arquivos duplicados com orientações diferentes dificulta a manutenção.

## Memória útil

Guarde decisões que alteram o trabalho: uma regra de negócio, por que uma biblioteca foi escolhida ou como reproduzir uma falha. Registre a evidência e atualize a informação quando o comportamento mudar.

Não transforme a documentação em uma transcrição de todas as conversas. Resumos antigos precisam ser conferidos contra os arquivos atuais. Senhas, tokens e bases de clientes não pertencem a modelos públicos.

O toolkit tem referências para memória do cliente, Obsidian e grafos de código. São opções para necessidades específicas; uma documentação curta pode ser suficiente.

Use os modelos de [projeto](../../modelos/pt/projeto.md), [decisões](../../modelos/pt/decisoes.md) e [verificação](../../modelos/pt/verificacao.md).
