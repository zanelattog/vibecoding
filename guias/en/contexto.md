# Keeping project context


When a conversation ends, the project still needs to make sense. Recording decisions in files helps the next person or agent work with what actually exists.

| Document | What to record |
| --- | --- |
| README | What the project does, how to run it and what is ready. |
| Product | Problem, audience, main workflow and acceptance criteria. |
| Project instructions | Valid commands, conventions and work boundaries. |
| Architecture | Responsibilities, data, integrations and important decisions. |
| Design | Visual patterns, states and accessibility needs. |
| Quality | Checks, results, known failures and limitations. |
| Setup | Dependencies, versions and configuration instructions. |

Reuse existing documents that already serve these purposes. Duplicate files with conflicting guidance make maintenance harder.

## Useful memory

Keep decisions that affect the work: a business rule, why a library was selected or how to reproduce a bug. Record evidence and update it when behavior changes.

Documentation should not become a transcript of every conversation. Check older summaries against current files. Passwords, tokens and customer databases do not belong in public templates.

The toolkit references client memory, Obsidian and code graphs. These are options for specific needs; short documentation may be enough.

Use the [project](../../modelos/en/projeto.md), [decisions](../../modelos/en/decisoes.md) and [verification](../../modelos/en/verificacao.md) templates.
